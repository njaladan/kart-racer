## Diagnosis

At the audit baseline, the game had modern rendering components, but its environment still communicated simple geometry and sparse composition. The gap was most visible in tree crowns, hill silhouettes, flat terrain, building faces, repetitive curbs and the abrupt transition from road to surrounding ground. Detailed karts and scanned materials could not compensate for these large forms.

The Wii reference demonstrates how coherent scenery and textured surfaces can make economical geometry convincing. The Mario Kart 8 reference adds richer foliage, terrain variation, softer local shading, stronger material separation and atmospheric layering. The proposed methods below aim to reproduce those visual cues efficiently; they do not claim to reproduce Nintendo's engine.

Already present at baseline: PBR materials; many color, normal and roughness maps; filtered environment reflections on karts; a 2048px sun shadow map; contact-shadow decals; a procedural sky; particles; animated scenery; instancing and static merging; MSAA and tone mapping; adaptive pixel density. The work below improves their use and supplies better artwork.

## Implemented across all courses

- Replaced many primitive landmarks and roadside props with downloaded, licensed SuperTuxKart assets. Each course pack records attribution, license evidence, byte size and SHA-256. Added near/mid/far vegetation variants where silhouettes dominate.
- Built course-specific scenery in all six sectors: layered trees and fields in Windmill, dense waterfront/city and working harbor structures, dunes/ruins/oasis dressing, and sculpted snowbanks, ridges and ski-lift scenery.
- Exported each assembled course scene to an offline Blender BVH bake. All four tracks now load a 512×512 indirect diffuse/AO texture plus a height map; the bake excludes direct sun so the live sun shadow is not counted twice. Output and source-scene hashes are recorded in each `assets/lighting/<course>/bake.json`.
- Added regional static batching, repeated-geometry instancing, preserved extra vertex channels, and grouped imported foliage LODs. Distance detail is quality-tier aware.
- Added course-specific reflection environments, material-scale surface variation, water response, height haze and shader-driven foliage wind. The adaptive quality controller uses measured frame time with hysteresis and can lower resolution, shadow/effect cost and local-light count, then recover after sustained healthy frames.
- Added optional restrained post-processing and bounded, non-shadowed local light pools. Bloom is reserved for higher quality tiers; transparent effects and particle pools remain bounded.
- Updated the course scene tests to verify finite geometry, real instancing and bounded total scene objects. Bake tests verify dimensions and hashes for all eight images.

The 60 FPS / 30 FPS goals below remain device targets, not measured guarantees. Headless capture confirms the new scenes render, but this environment does not provide representative integrated-GPU performance measurements.

## Baseline implementation findings

- `game-scene.js`: one shadowed sun, hemisphere fill and a weak rim light. No course lightmap setup. Broad fill supplies light without knowing whether an object is under a roof or inside a recess.
- `vertex-shading.js`: `bakeVertexShade` derives shade from height and normal direction. It does not calculate obstruction, neighboring geometry or bounced light. It skips geometries that already have vertex colors.
- `living-assets.js`: imported props use the packed ARM map for roughness/metalness but do not connect its AO channel. Add AO with an appropriate UV setup.
- `visuals.js`: static merging preserves position, normal, base UV and color only. It would discard the extra UV channels needed by some AO/lightmap setups. Preserve channels and allocate unique lightmap atlas regions before adding baked lighting.
- `course-kit.js`: flattening followed by material-wide merging can create batches spanning much of the course. Their large bounds weaken camera and shadow-frustum rejection. Windmill nature already has section batches; use this idea throughout, with smaller regions where necessary.
- Asset allocation is uneven: the four bundled base tree meshes contain only 258–588 vertices each, while the imported street lamp has 61,014 vertices and the planter has 24,282. These are source vertex counts, not measured frame totals. Decimate and LOD small imported props, then allocate more detail to trees, terrain and architectural outlines that dominate the image.
- `shared-assets.js` filters a single sky-reflection image at startup; the same source is used across courses. A night environment with building/light colors would be a better fit for Harbor.
- `frame-loop.js`: adaptive density lowers resolution when average frame time exceeds 25 ms (about 40 FPS). It uses clamped simulation delta, lowers only, and leaves shadow/effect complexity unchanged. Use actual frame timing, smoothing/hysteresis, recovery, and separate quality tiers for a 60 FPS goal.

Three.js supports [lightmaps, AO and environment maps](https://threejs.org/docs/pages/MeshStandardMaterial.html). Its [shadow guide](https://threejs.org/manual/pages/shadows.html) explains why offline lighting and limited real-time shadow lights are economical. [KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html) supports textures that remain GPU-compressed; WebP download compression alone does not provide that GPU memory benefit. Check APIs against the project's bundled Three.js r180 when implementing.

## Lighting and baking approach

The current offline solver exports the assembled static course meshes, runs BVH hemisphere visibility and colored surface bounce, then writes an indirect-light/AO map and a height map. At runtime, a world-space projection samples them near the ground; there is no extra per-asset lightmap UV channel to preserve. Authored lamp pools are baked, while the real-time sun supplies direct light and dynamic shadows. The broad height map is a compact compromise: it gives each complete course indirect shading without the seams and authoring overhead of per-object atlases.

Moving karts use filtered course reflection environments and a capped set of the nearest non-shadowed lamp lights. The local-light count, sun-shadow resolution, weather density and post-processing respond to quality tiers. This keeps shade transitions and night pools visible without baking direct sunlight twice.

The 512px bake resolution and eight hemisphere samples favor memory and bake time over close-up lightmap precision. Fine contact detail still comes from normal maps, vertex shading and decals. A higher-resolution regional atlas or separately baked static sun shadows would be future options after device profiling.

## Browser performance

The renderer targets 60 FPS on higher settings and 30 FPS on the performance tier; these remain goals, not measured guarantees. Sustained frame timing now drives resolution and quality-tier changes with hysteresis and recovery. The full test suite checks all course geometry, instancing, UV channels, bake files and simulation behavior. Chromium headless captures verify all four courses render, but its software renderer is not a substitute for profiling a representative integrated GPU. Measure frame-time distributions, visible draw calls, triangles and texture memory on target hardware before raising the bake or post-processing cost.

The recommended balance is better models where outlines matter, better textures where surface detail matters, and sophisticated lighting calculated mostly before the player loads the game.
